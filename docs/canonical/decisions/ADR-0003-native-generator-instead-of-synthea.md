# ADR-0003 — A native deterministic generator replaces Synthea

- **Status:** Accepted
- **Date:** 2026-08-31
- **Scope:** Synthetic corpus generation (`packages/data/`), Sprint 01, Gate G3
- **Owner section:** [04_data_card.md](../04_data_card.md) § Synthetic data plan → Generator
- **Supersedes:** the sentence "Use Synthea to generate privacy-safe FHIR records, then run a
  deterministic adapter that…" in [04_data_card.md](../04_data_card.md). Everything else in
  that section — the adapter's responsibilities, prototype scale, normal patterns, injected
  patterns, labels, splits, and leakage controls — stands unchanged and is now satisfied by
  the native generator instead of by an adapter over Synthea output.

## Context

`04_data_card.md` specifies Synthea as the source of clean records, with a deterministic adapter
that re-pseudonymizes, subsets, builds a billing layer, and injects labelled patterns.

Three facts, established while starting Sprint 01:

1. **Synthea is not installed and this machine has no Java Runtime.** Synthea is a Java
   application; standing it up means a JDK install, the Synthea distribution, and a generation
   run, before any project code is written. Gate G3 falls on 2 September.

2. **The adapter would discard most of what Synthea provides.** Synthea emits US-shaped FHIR:
   US demographics, US care pathways, SNOMED/LOINC coding, and USD costs. The documented adapter
   already re-pseudonymizes every identifier, selects a narrow subset, and **constructs the
   entire Account / ChargeItem / Invoice / Claim layer from scratch** — the billing layer that
   every one of the four risk modes is defined over does not come from Synthea at all.

3. **The data card already concedes the realism does not transfer.** Its own words: Synthea's
   "epidemiology, care pathways, and billing assumptions are not representative of JKN. The
   adapter must never claim otherwise."

Taken together, Synthea's contribution is clinical plausibility that the adaptation largely
destroys, bought at the price of a toolchain the project cannot currently run.

## Decision

1. `packages/data/` contains a **native deterministic generator** that emits `CanonicalBundle`
   records directly, with no intermediate FHIR representation and no Java dependency.
2. Every obligation the data card places on the adapter is carried over unchanged: the demo
   pseudonym namespace, the documented resource subset, the constructed billing relationships,
   internally consistent illustrative amounts, and a machine-readable manifest recording seed
   and version.
3. All **normal patterns**, **injected patterns**, **labels**, **splits**, and **leakage
   controls** in `04_data_card.md` remain binding and are now the generator's responsibility.
4. Determinism is stricter than before: one seed reproduces the corpus byte-for-byte, with no
   dependency on an external tool's version or its own RNG.
5. Synthea is **not ruled out**. A Synthea import path may be added later as an alternative
   front end to the same canonical output. This ADR removes it as a prerequisite, not as an
   option.

## Consequences

- Gate G3 stops depending on installing and learning an external toolchain.
- Reproducibility improves: no "which Synthea version produced this?" question can arise.
- **The proposal loses a claim it was going to make.** Slide 8 planned to cite Synthea's Apache
  2.0 licence [E11] as evidence of a recognised, privacy-safe source. That claim must be
  removed, not softened. The honest replacement is narrower and still true: the corpus is
  wholly synthetic, generated by project code, seeded and reproducible, and *no real patient
  record of any origin was involved*. → [09_proposal_evidence_map.md](../09_proposal_evidence_map.md) slide 8.
- The generator now carries the burden of clinical plausibility that Synthea would have
  supplied. It must not be described as clinically realistic. The data card's prohibition
  applies with full force to our own generator: **this dataset does not represent JKN
  prevalence or real provider behaviour**, and the generated distributions are a test-design
  choice, not an empirical finding.
- A reviewer may reasonably ask why a well-known tool was not used. The answer above is the
  answer to give: it was evaluated, and the part of it that mattered would not have survived
  the adaptation the data card already required.

## Reversal

Adding a Synthea front end later does not require a new ADR — it is explicitly permitted by
decision 5. Making Synthea *mandatory* again would.
