# 23. Risk Register — How We Could Lose This Competition
| Risk | Early warning signal | Mitigation | Owner |
|---|---|---|---|
| Weak problem evidence | Deck uses generic “fraud is huge” claims | Anchor to official modes, current integration policy, and JKN scale; say fraud loss is not established | M3 |
| Generic AI solution | Readers summarize it as “AI fraud dashboard/chatbot” | Lead with claim-line evidence path, human action, and measurable hybrid-vs-rule proof | M2 |
| Prior-solution overlap | Proposal resembles PRO-CLAIM by name/function | Acknowledge public predecessor; differentiate evidence graph, provenance, non-generative core; ask organizer | M3 |
| Unrealistic BPJS integration | Diagrams show live APIs/production deployment | Label published-schema compatibility and future authorized pilot; no connection claim | M1 |
| Inaccessible data | BPJS sample access stalls or lacks fields | Keep sample off critical path; use Synthea adapter/injections and disclose limitations | M2 |
| Synthetic overclaim | Metrics appear without a synthetic label | Watermark every result; include “demonstrates/does not” table; block national projections | M3 |
| Leakage inflates results | Near-perfect metrics or ID/order importance | Grouped splits, trivial leakage probe, hidden-manifest exclusion, manual error review | M1 |
| Low differentiation | Pitch focuses on anomaly model | Make evidence provenance, counter-evidence, and disposition the product core | M2 |
| AI is unnecessary | Hybrid does not beat rules-only | Remove ML and present appropriate rules-first engineering; keep similarity only if valuable | M1 |
| Poor evaluation | Only AUROC or one cherry-picked case | Frozen baselines, PR/precision@K, FP/100, per-mode results, latency, limitations | M1 |
| Feature bloat | More than four primary pages or inactive menus | Evidence-yield rule; one-in/one-out scope; Gate 5 clean path | M3 |
| Weak UI | Reviewer cannot find why a case is flagged | Reason before score; Figma comprehension test; task-directed evidence path | M2 |
| Privacy problem | Real identifiers or raw text appear in logs/screens | Synthetic only, pseudonymous UI, redaction tests, minimization, no external LLM | M1/M3 |
| False accusation | UI says “fraudulent claim/hospital” | Controlled vocabulary: risk, anomaly, evidence gap, human confirmation | M3 |
| Clinical overreach | Rules judge medical necessity or coding without expertise | Structural evidence only; expert-validation backlog; remove unsupported rule | M3 |
| Unverifiable claims | Slide value has no source/artifact | Proposal claim ledger; criterion owner sign-off; delete unsupported numbers | M3 |
| Proposal story failure | Technology appears before problem/user | Use 16-slide arc; rehearse 30-second/3-minute narrative | M3 |
| Technical demo failure | Clean install/reset is unreliable | Docker/local-first, deterministic fixtures, health/reset scripts, recorded fallback | M1 |
| Team bottleneck | Member 2 waits for API or M3 waits for results | Contract-first fixtures, parallel tracks, daily integration, explicit owners | M3 |
| Scope explosion | New mode/model added after 5 Sep | Freeze four modes; require judging evidence and one-in/one-out removal | M3 |
| Official-rule mistake | Disputed mode/category enters deck | Avoid disputed “Kolusi & Surat Fiktif”; final compliance matrix check | M3 |
| File/upload failure | PDF >10 MB or renders differently | Export and test by 16 Sep; compress images; upload on 18 Sep; save receipt | M2/M3 |
